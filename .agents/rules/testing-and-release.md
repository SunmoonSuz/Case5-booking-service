# Тестирование и ручной выпуск

- Любое Must-have требование должно быть связано с одним или более тестами или документированной ручной проверкой.
- Новая бизнес-логика должна иметь unit-тесты; взаимодействия компонентов — интеграционные тесты; критичные end-user flows — E2E или обоснованную ручную проверку.
- Для каждого дефекта добавляй регрессионную проверку.
- Выбирай уровень тестирования по профилю: backend — API/component/contract; Android — unit/UI/instrumented/device/lifecycle/permission checks по применимости; web — UI/browser E2E для утверждённых сценариев. Не требуй не включённые в scope компоненты.
- Тесты должны содержать meaningful assertions, проверять результат и негативные случаи. Не допускаются пустые тесты, безусловные `skip`, тесты, проверяющие только вызов mock без бизнес-результата, и tautological assertions.
- Тесты запускаются фактически. Сохраняй команды и вывод/сводку. Не симулируй успешный запуск.
- Не скрывай нестабильность повторным запуском без расследования.
- Пробный релиз только вручную после QA, review и заполненного release checklist.
- CI/CD и автоматический деплой вне текущего scope.
