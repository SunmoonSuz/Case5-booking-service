## 1. Product Brief

Сервис онлайн-записи на услуги — это full-stack веб-приложение для одного заведения (Single-tenant), позволяющее клиентам в режиме 24/7 выбирать услуги, мастеров и свободные слоты, оформлять заявки на бронирование и управлять своими визитами через Личный кабинет.

Каждая новая заявка создаётся в статусе ожидания подтверждения (`PENDING`) и блокирует временной слот мастера от повторного бронирования. Серверный бэкенд обеспечивает строгую транзакционную изоляцию, полностью исключая двойное бронирование (овербукинг) при конкурентных параллельных запросах. Администратор заведения через выделенную панель управления ведёт каталог услуг, мастеров, расписание и осуществляет модерацию заявок: подтверждает (`CONFIRMED`), отклоняет (`REJECTED`), отменяет (`CANCELLED`) или отмечает визиты завершёнными (`COMPLETED`).

## 3. Scope MVP / Out of Scope

### Scope MVP
1. Регистрация, аутентификация и сессия по связке Email + Пароль (с криптографическим солением). Безопасный Logout.
2. Каталог услуг (название, описание, длительность 30/60 мин, стоимость).
3. Карточки мастеров и привязка услуг к мастерам.
4. Управление рабочим графиком мастеров администратором (дни недели, часы смены).
5. Динамический расчёт свободных слотов с фильтрацией слотов в статусах $S_{active}$ и слотов в прошлом.
6. Оформление заявки на бронирование со статусом `PENDING`.
7. Аппаратная защита от двойного бронирования на бэкенде (HTTP 409 Conflict при коллизиях, динамическое обновление UI).
8. Личный кабинет клиента с историей и отменой активных записей.
9. Web UI Администратора для модерации заявок (`CONFIRMED`, `REJECTED`, `CANCELLED`, `COMPLETED`) и настройки расписания.
10. Адаптивная верстка (Mobile-first, экраны от 360px).

### Out of Scope
- Native Android и iOS мобильные приложения (`DEC-001`).
- Онлайн-эквайринг, депозиты, предоплата и фискализация (`DEC-008`).
- Платные SMS-шлюзы и боты мессенджеров (`DEC-008`).
- Интеграции с Google Calendar / Apple Calendar, CRM и внешними складскими системами (`DEC-008`).
- Multi-tenancy (сеть филиалов).
- Автоматический CI/CD pipeline и облачный деплой.

## 5. Product / Implementation Profile

- **Project type:** `FULL_STACK` (Kotlin Backend + Web Frontend) (`DEC-001`).
- **Нужен ли native Android app:** `NO` (`OUT OF SCOPE`).
- **Нужен ли web frontend:** `YES` (Mobile-first адаптивный веб).
- **Нужен ли backend:** `YES` (Kotlin REST API).
- **Тип результата / артефакты:** Backend API сервис + Web UI приложение + СУБД + Документация и автотесты.
- **Предпочтительный backend стек:** Язык **Kotlin** (Java 17/21, Gradle). Конкретный фреймворк (Spring Boot 3.x или Ktor) определяется инженерами.
- **Frontend стек:** React / Vue / Svelte / Vite с Tailwind CSS или модульным CSS.
- **СУБД:** Реляционная СУБД с поддержкой транзакций ACID (рекомендуется PostgreSQL).
- **Ограничения по технологиям:** Защита от овербукинга должна выполняться на уровне бэкенда/хранилища данных, а не в UI.

## 6. Non-Functional Constraints

- **`NFR-001` (Concurrency & Data Integrity):** При отправке 20 одновременных запросов с разницей $\le 50$ мс создаётся ровно 1 бронирование (`201 Created`), остальные получают `409 Conflict`.
- **`NFR-002` (Platform Profile):** Профиль `FULL_STACK`. Мобильные приложения исключены.
- **`NFR-003` (Usability):** Адаптивность от 360px до 1920px. Поддержка браузеров Chrome, Safari, Firefox.
- **`NFR-004` (Security):** Солевое хэширование паролей (Argon2id/BCrypt), разделение прав доступа (RBAC на `/api/v1/admin/*`).
- **`NFR-005` (Timezone):** Хранение меток строго в UTC (ISO-8601), отображение клиенту в локальном времени заведения.
- **`NFR-006` (Performance):** Расчёт сетки слотов $\le 300$ мс (p95) при 50 одновременных пользователях.

## 7. Users, Roles and Permissions

- **Гость (`ACTOR-001`):** Просмотр каталога, мастеров и доступных слотов. Бронирование требует входа/регистрации.
- **Клиент (`ACTOR-002`):** Создание заявок (`PENDING`), просмотр своих бронирований в ЛК, отмена активных заявок (`CANCELLED`), Logout. Доступ к чужим бронированиям и админке закрыт.
- **Администратор (`ACTOR-003`):** Полный доступ к управлению услугами, мастерами, расписанием, модерации входящих заявок (`CONFIRMED`, `REJECTED`), отмене подтверждённых записей (`CANCELLED`) и завершению визитов (`COMPLETED`).

## 8. Data, Integrations and External Dependencies

### Модель сущностей
- `User`: `id`, `email`, `password_hash`, `role` (`CLIENT`, `ADMIN`), `name`, `phone`, `created_at`.
- `Master`: `id`, `name`, `description`, `is_active`.
- `Service`: `id`, `name`, `description`, `duration_minutes` (30/60 мин), `price`, `is_active`.
- `MasterService`: `master_id`, `service_id` (M:N).
- `MasterSchedule`: `id`, `master_id`, `day_of_week` (1..7), `start_time`, `end_time`.
- `Booking`: `id`, `client_id`, `master_id`, `service_id`, `start_time` (UTC), `end_time` (UTC), `status`, `created_at`, `updated_at`.

### Жизненный цикл бронирования
- $S_{active} = \{ \text{PENDING}, \text{CONFIRMED} \}$ (слот удерживается).
- $S_{inactive} = \{ \text{REJECTED}, \text{CANCELLED}, \text{COMPLETED} \}$ (слот свободен/в архиве).
- Переходы:
  - `[*] -> PENDING` (создание заявки клиентом).
  - `PENDING -> CONFIRMED` (подтверждение администратором).
  - `PENDING -> REJECTED` (отклонение администратором, слот освобождается).
  - `PENDING -> CANCELLED` (отмена клиентом, слот освобождается).
  - `CONFIRMED -> CANCELLED` (отмена клиентом или администратором, слот освобождается).
  - `CONFIRMED -> COMPLETED` (завершение визита администратором).

### Внешние интеграции
Внешние зависимости и интеграции в рамках MVP отсутствуют (`DEC-008`).

## 9. Proposed Technical Considerations (Рекомендации разработчикам)

*Данные соображения являются рекомендательными и не сковывают команду разработки:*
1. **Защита от овербукинга на уровне СУБД (PostgreSQL):**
   - *Вариант A:* Использование транзакции с пессимистической блокировкой строки мастера (`SELECT ... FROM masters WHERE id = ? FOR UPDATE`).
   - *Вариант B:* Использование диапазонных типов данных `tstzrange` и составного exclusion constraint:
     ```sql
     ALTER TABLE bookings ADD CONSTRAINT no_overlapping_bookings
     EXCLUDE USING gist (
       master_id WITH =,
       tstzrange(start_time, end_time, '[)') WITH &&
     ) WHERE (status IN ('PENDING', 'CONFIRMED'));
     ```
   При нарушении ограничения СУБД выбрасывает исключение, которое бэкенд транслирует в HTTP 409 Conflict.
2. **Инициализация суперпользователя:**
   Предусмотреть Liquibase/Flyway миграцию или класс инициализации (`CommandLineRunner`), создающий администратора по умолчанию (`admin@example.com` / `admin12345`) при первом запуске, если таблица пользователей пуста (`ASM-007`).

## 11. Risks and Mitigations

| ID | Риск | Критичность | Меры снижения |
|---|---|---|---|
| `RISK-001` | Гонка за слот (Race condition) $\to$ овербукинг. | Critical | Транзакционная изоляция на бэкенде, автотест `AC-003` (20 параллельных потоков). |
| `RISK-002` | Рассинхронизация часовых поясов. | High | Хранение меток строго в UTC (ISO-8601), автотест `AC-010`. |
| `RISK-003` | Раздувание скоупа (Scope creep). | High | Строгий `OUT OF SCOPE` для платежей, SMS и нативных мобильных приложений. |
| `RISK-004` | Неудобство UI на смартфонах. | High | Mobile-first верстка с тестированием экранов от 360px (`NFR-003`). |
| `RISK-005` | Зависание заявки в статусе `PENDING`. | Medium | Бейдж нерассмотренных заявок в UI админа, право клиента отменить заявку в ЛК (`REQ-009`). |
