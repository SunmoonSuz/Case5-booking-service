# Quality Gates: Definition of Ready / Definition of Done

## Definition of Ready (DoR) — задача допускается к реализации, когда

- [ ] Есть ссылка на утверждённую версию спецификации и перечислены связанные `REQ-*`.
- [ ] У каждого требования в scope есть один или несколько проверяемых `AC-*`.
- [ ] Определены пользователь/роль, предусловия, ожидаемый результат и ошибки для затрагиваемого сценария.
- [ ] Указаны ограничения, интеграции, зависимости и затрагиваемые данные.
- [ ] Нет открытых вопросов, блокирующих реализацию; остальные вопросы явно назначены владельцам.
- [ ] Scope и out of scope ограничены; понятно, какие модули/контракты могут измениться.
- [ ] Тестируемость требования подтверждена; нет формулировок, которые невозможно проверить.
- [ ] Для существенного технического риска запланировано исследование/ADR до изменения production-кода.

Если любой пункт не выполнен, задача получает `BLOCKED` или `NEEDS_CLARIFICATION`; разработчик не должен заполнять пробелы догадкой.

## Definition of Done (DoD) — задача считается завершённой, когда

- [ ] Все связанные `REQ-*` реализованы и проверены по acceptance criteria.
- [ ] Добавлены unit-тесты для новой бизнес-логики и регрессионные тесты для исправлений.
- [ ] Integration/API/contract/E2E/manual проверки выполнены там, где это требуется характером требования. Для `BACKEND_ONLY` проверяй backend/API; для Android scope — UI/instrumented/device/lifecycle проверки в применимом объёме; для web scope — browser/UI E2E для утверждённых сценариев. Недоступные проверки помечены `NOT RUN`, а не `PASS`. Load/stress проверки добавляются только при наличии соответствующих NFR или рисков.
- [ ] Тесты действительно запущены; команды и фактические результаты задокументированы. Непроверенное помечено `NOT RUN`.
- [ ] Нет пустых assertions, безусловных skips и тестов-заглушек, которые не подтверждают ожидаемое поведение.
- [ ] Код соответствует стандартам проекта, не содержит неоправданной сложности, нарушений архитектурных границ и известных критичных уязвимостей.
- [ ] Документация, конфигурационные примеры, API/миграции и инструкции обновлены, если они затронуты.
- [ ] QA report имеет `PASS` или `PASS WITH KNOWN ISSUES`; нет открытых BLOCKER/CRITICAL. MAJOR допускается только при явно зафиксированном принятии риска владельцем продукта.
- [ ] Strict code review имеет `APPROVE`; блокирующие замечания устранены и перепроверены.
- [ ] Изменения ограничены согласованным scope; все отклонения/решения зафиксированы.

## Ориентиры по метрикам

- Покрытие тестами не является самостоятельной гарантией качества. Как стартовый ориентир можно использовать 70–80% для релевантной логики и стремиться примерно к 80% на изменяемых бизнес-модулях, если стек позволяет достоверно измерить покрытие. Для критичных правил важнее полное покрытие значимых ветвей и негативных сценариев, а не достижение красивого процента.
- Следи за цикломатической сложностью, дублированием и code smells как сигналами для анализа, а не как механическими запретами.
- Не рефактори unrelated части ради улучшения метрики в рамках узкой функциональной задачи.

## Release Gate

Ручной пробный выпуск разрешён, когда DoD выполнен, QA и review имеют положительные вердикты, известные риски приняты владельцем продукта, а `docs/release/RELEASE-CHECKLIST.md` заполнен. CI/CD и автоматический деплой в этот gate не входят.
