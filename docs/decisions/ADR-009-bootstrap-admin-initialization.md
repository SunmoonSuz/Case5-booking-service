# ADR-009: Инициализация первичной учетной записи администратора

- Status: `ACCEPTED`
- Date: `2026-11-03`
- Decision owner: `Security Architect / Lead Backend Engineer`

## Context

В соответствии с `REQ-001` публичная регистрация создаёт исключительно пользователей с ролью `CLIENT`. Клиент не может самостоятельно повысить свои привилегии до роли `ADMIN`.
Для функционирования сервиса и демонстрации административных сценариев (`SCN-005`, `AC-006`–`AC-009`) в системе должен присутствовать как минимум один пользователь с ролью `ADMIN`.
В допущении `ASM-007` и `IMPLEMENTATION-BRIEF.md` (раздел 10) подчеркивается:
- Учётные данные `admin@example.com` / `admin12345` из handoff являются лишь техническим примером;
- Нельзя «вшивать» пароли в открытом виде в исходный код или миграции;
- Пароль администратора должен хэшироваться тем же стойким алгоритмом (BCrypt), что и пароли клиентов;
- Пароль ни при каких обстоятельствах не должен попадать в логи приложения.

## Decision

Рекомендуется:

1. **Механизм инициализации:**
   - Компонент `AdminBootstrapRunner` (`ApplicationRunner`), выполняющийся при старте приложения после завершения миграций Flyway.
2. **Проверка существования:**
   - Компонент проверяет наличие в таблице `users` хотя бы одной записи с `role = 'ADMIN'`:
     ```kotlin
     if (userRepository.existsByRole(Role.ADMIN)) {
         logger.info("Admin user already exists. Skipping bootstrap initialization.")
         return
     }
     ```
3. **Источники конфигурации и создание сущности:**
   - Переменные окружения:
     - `APP_BOOTSTRAP_ADMIN_EMAIL` (по умолчанию для dev-профиля: `admin@example.com`);
     - `APP_BOOTSTRAP_ADMIN_PASSWORD` (по умолчанию для dev-профиля: `admin12345`).
   - Для production-профиля (`prod`) при отсутствии переменных инициализация суперпользователя блокируется с фатальной ошибкой конфигурации или требует ручного задания надежного пароля.
   - Обязательные поля `NOT NULL` сущности `User` заполняются значениями по умолчанию: `name = "Administrator"`, `phone = "+70000000000"`, что предотвращает ошибку целостности данных (`DataIntegrityViolationException`) при первичном старте:
     ```kotlin
     val admin = User(
         email = bootstrapEmail.lowercase().trim(),
         passwordHash = passwordEncoder.encode(bootstrapPassword),
         role = Role.ADMIN,
         name = "Administrator",
         phone = "+70000000000"
     )
     userRepository.save(admin)
     ```
4. **Хэширование и безопасность:**
   - Пароль хэшируется через внедряемый бин `PasswordEncoder` с динамической генерацией соли.
   - В логах фиксируется только факт: `"Bootstrap admin user created with email: {}"`. Значение пароля никогда не логируется.

## Alternatives considered

| Option | Benefits | Costs/Risks |
|---|---|---|
| **Вариант 1: `ApplicationRunner` + ENV-переменные (Рекомендуется)** | 1. Пароль хэшируется текущим алгоритмом приложения на лету.<br>2. Легко переопределяется через переменные окружения без изменения SQL-скриптов.<br>3. Идемпотентность: повторный запуск приложения не перезаписывает измененный пароль администратора. | Выполняется в коде приложения, а не чистым SQL. |
| **Вариант 2: SQL-миграция Flyway (`V2__seed_admin.sql`) с предрассчитанным BCrypt-хэшем** | 1. Создается сразу на уровне СУБД до старта Java-кода. | Хэш жестко фиксирован в файле репозитория; изменение пароля требует новой миграции; раскрытие хэша в открытом Git-репозитории. |

## Consequences

- На чистой базе данных при первом запуске автоматически создается готовый аккаунт администратора для локального тестирования и ручного приемочного смоук-теста.
- Учетные данные администратора защищены в соответствии с `NFR-004`.

## Requirements affected

- `REQ-002`, `NFR-004`, `ASM-007`, `SCN-005`, `AC-008`.
