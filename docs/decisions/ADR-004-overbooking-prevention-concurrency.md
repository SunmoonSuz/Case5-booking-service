# ADR-004: Механизм защиты от овербукинга и обработка конкурентных запросов

- Status: `ACCEPTED`
- Date: `2026-11-03`
- Decision owner: `Lead Backend Engineer / System Architect`

## Context

Защита от двойного бронирования (овербукинга) к одному специалисту на пересекающиеся временные интервалы — главный инвариант целостности продукта (`GOAL-002`, `REQ-006`, `REQ-007`, `NFR-001`, `BR-001`, `BR-002`).

Параметры и ограничения инварианта:
1. Ресурсом бронирования является мастер (`master_id`).
2. Временной интервал задаётся как полуинтервал $[T_{start}, T_{end})$, где $T_{end} = T_{start} + Duration(Service)$.
3. Смежные интервалы допустимы и не конфликтуют: $[10:00, 11:00)$ и $[11:00, 12:00)$ к одному мастеру валидны (`AC-EDGE-001`).
4. Частичное перекрытие интервалов недопустимо: $[10:00, 11:00)$ и $[10:30, 11:30)$ конфликтуют (`AC-EDGE-002`).
5. Активными бронированиями, блокирующими слот, являются только статусы из множества $S_{active} = \{ \text{PENDING}, \text{CONFIRMED} \}$.
6. Статусы $S_{inactive} = \{ \text{REJECTED}, \text{CANCELLED}, \text{COMPLETED} \}$ освобождают слот и не должны препятствовать новым бронированиям (`BR-003`).
7. Требование `NFR-001` / `AC-003`: при 20 одновременных запросах ($\le 50$ мс) ровно один создает запись (`201 Created`), ровно 19 получают отказ (`409 Conflict`), в БД образуется ровно одна запись.
8. Проигравшие запросы не должны оставлять «фантомных» или частично созданных записей в БД.

Handoff предлагает два подхода:
- Вариант A: Транзакционная блокировка строки мастера (`SELECT ... FOR UPDATE`).
- Вариант B: PostgreSQL GiST Exclusion Constraint с диапазоном `tstzrange` и расширением `btree_gist`.

## Decision

Рекомендуется применить **эшелонированную защиту (Defense-in-Depth)**:

### 1. Фундаментальный уровень (База данных): GiST Exclusion Constraint
В миграции схемы БД создаётся расширение `btree_gist` и частичный exclusion constraint на таблицу `bookings`:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT no_overlapping_active_bookings
EXCLUDE USING gist (
  master_id WITH =,
  (tstzrange(start_time, end_time, '[)')) WITH &&
) WHERE (status IN ('PENDING', 'CONFIRMED'));
```

**Обоснование:**
- Выражение диапазона `(tstzrange(start_time, end_time, '[)'))` обязательно заключается в круглые скобки в соответствии с синтаксисом PostgreSQL `EXCLUDE USING`.
- Оператор `&&` проверяет пересечение полуинтервалов точно по правилу $start_1 < end_2 \land start_2 < end_1$. Смежные интервалы $[10:00, 11:00)$ и $[11:00, 12:00)$ имеют пустое пересечение и не вызывают ошибку.
- Предикат `WHERE (status IN ('PENDING', 'CONFIRMED'))` автоматически исключает из проверки отмененные, отклоненные и архивные записи.
- Ограничение действует на уровне ядра СУБД: физически невозможно создать овербукинг ни через приложение, ни через параллельные потоки, ни через прямой SQL.

### 2. Прикладной уровень (Серверное приложение):
- Процедура бронирования выполняется в транзакции `@Transactional(isolation = Isolation.READ_COMMITTED)`.
- Перед вставкой сервис выполняет пре-валидацию (проверяет график работы мастера, активность услуги и мастера, отсутствие бронирования в прошлом $T_{start} > T_{now}$).
- Вызов `bookingRepository.saveAndFlush(...)` форсирует немедленную отправку SQL INSERT до завершения метода, гарантируя валидацию ограничения в точке вызова.
- При попытке одновременной вставки перекрывающегося интервала PostgreSQL отклоняет второй запрос с SQLSTATE `23P01` (`exclusion_violation`).
- Серверный слой перехвата исключений (`@RestControllerAdvice`) ловит `DataIntegrityViolationException` / `PSQLException` с проверкой имени ограничения `no_overlapping_active_bookings`, откатывает транзакцию и выбрасывает доменное исключение `SlotAlreadyBookedException`.
- Клиенту возвращается HTTP `409 Conflict` со стандартизированным телом:
  ```json
  {
    "error": "SLOT_ALREADY_BOOKED",
    "message": "Выбранный слот уже занят другим клиентом. Пожалуйста, выберите другое время."
  }
  ```
- Никакие внутренние SQL-ошибки или трассировки стека клиенту не раскрываются.

### 3. Автоматизированная верификация и конфигурация пула соединений:
- **Размер пула HikariCP:** Для выполнения теста `AC-003` (20 параллельных запросов) пул соединений настраивается на `maximum-pool-size = 30` и `connection-timeout = 20000` (ADR-003), чтобы исключить `ConnectionTimeout` и гарантировать чистый возврат 409 Conflict.
- Реализация теста `AC-003` с использованием `Testcontainers` и `java.util.concurrent.CyclicBarrier` / виртуальных потоков: 20 потоков синхронно вызывают эндпоинт бронирования одного слота. Проверяется ровно 1 успешный `201`, ровно 19 кодов `409`, и `SELECT count(*) FROM bookings WHERE master_id = ? AND status IN ('PENDING', 'CONFIRMED')` возвращает ровно 1.

## Alternatives considered

| Option | Benefits | Costs/Risks |
|---|---|---|
| **Вариант 1: GiST Exclusion Constraint (Рекомендуется как базовый инвариант)** | 1. 100% математическая гарантия инварианта на уровне СУБД.<br>2. Автоматическая поддержка произвольных интервалов и длительностей (30 и 60 мин).<br>3. Не блокирует создание записей к другим мастерам или к этому же мастеру на другие даты.<br>4. Высокая производительность и низкая задержка. | Привязка к PostgreSQL и расширению `btree_gist` (PostgreSQL уже утвержден в профиле проекта). |
| **Вариант 2: Пессимистическая блокировка строки мастера (`SELECT ... FOR UPDATE`)** | 1. Работает в любой реляционной СУБД.<br>2. Исключение формируется на уровне Java без ловли SQL-ошибки. | 1. Избыточная сериализация: блокировка строки мастера сериализует бронирования на разные дни/месяцы вперед, создавая бутылочное горлышко.<br>2. Риск забыть блокировку в других операциях (например, при переносе/редактировании).<br>3. Потенциальные дедлоки при сложных транзакциях. |
| **Вариант 3: Оптимистическая блокировка (версионирование мастера)** | 1. Не держит блокировок в БД. | Высокий процент повторов (retry storms), сложная логика разрешения конфликтов при 20 одновременных запросах, не защищает от частичных перекрытий. |

## Consequences

- Требуется наличие PostgreSQL с поддержкой `btree_gist`.
- Таблица `bookings` содержит типизированные колонки `start_time TIMESTAMPTZ` и `end_time TIMESTAMPTZ`.
- Конкурентный автотест `AC-003` становится обязательным элементом Quality Gate до допуска к ручному релизу.
