# ADR-007: Конфигурация часового пояса и обработка времени

- Status: `ACCEPTED`
- Date: `2026-11-03`
- Decision owner: `Lead Backend Engineer / System Architect`

## Context

Сервис онлайн-записи обслуживает физическое заведение (Single-tenant).
Требования:
- `NFR-005`: все метки времени в базе данных и API должны храниться и передаваться в формате ISO-8601 UTC.
- `ASM-006`: все бизнес-операции заведения привязаны к единому часовому поясу. Пользователю время отображается в локальном времени заведения, а не автоматически в поясе его устройства (клиент может бронировать визит из другой таймзоны перед поездкой).
- `AC-010`: автотест проверяет, что бронирование на `2026-11-10 14:00` в поясе `UTC+3` сохраняется в БД строго как `2026-11-10T11:00:00Z` и возвращается клиенту с корректной конвертацией в локальные `14:00`.
- В handoff не был зафиксирован конкретный IANA-идентификатор таймзоны (упоминался пример `UTC+3`).

## Decision

Рекомендуется:

1. **Идентификатор часового пояса:**
   - Использовать стандартные IANA Time Zone IDs (например, `Europe/Moscow`).
   - Конфигурировать через переменную окружения `APP_TIMEZONE` со значением по умолчанию `Europe/Moscow` (что соответствует `UTC+3` без сезонного перевода часов).
2. **Серверное время и хранение:**
   - В PostgreSQL все временные колонки объявляются как `TIMESTAMPTZ` (timestamp with time zone), JVM работает в UTC (`TimeZone.setDefault(TimeZone.getTimeZone("UTC"))`).
   - В Kotlin-сущностях используются типы `java.time.Instant` для меток событий и границ бронирования, а также `java.time.LocalTime` для регулярных графиков работы (`MasterSchedule.start_time`, `MasterSchedule.end_time`).
   - Проверка текущего времени ($T_{start} \le T_{now}$) выполняется через внедряемый бин `java.time.Clock`, что позволяет легко замораживать и сдвигать время в тестах (`AC-EDGE-005`, `AC-EDGE-008`).
3. **API-контракты:**
   - Все поля дат со временем сериализуются в формате ISO-8601 UTC: `2026-11-10T11:00:00Z`.
   - Сервер предоставляет конфигурационный эндпоинт `GET /api/v1/config` (или отдает часовой пояс в эндпоинте каталога/доступности), сообщая фронтенду IANA-зону заведения.
4. **Клиентская часть (Web Frontend):**
   - Фронтенд форматирует даты и слоты для отображения пользователю с принудительным указанием часового пояса заведения (библиотека `date-fns-tz` или нативный `Intl.DateTimeFormat` с опцией `{ timeZone: venueTimeZone }`).

## Alternatives considered

| Option | Benefits | Costs/Risks |
|---|---|---|
| **Вариант 1: IANA Time Zone через `APP_TIMEZONE` + UTC в БД/API (Рекомендуется)** | 1. 100% покрытие требований `NFR-005` и `AC-010`.<br>2. Корректная обработка исторических дат и возможных изменений правил таймзон.<br>3. Легкость настройки для любого региона через ENV-переменную.<br>4. Внедряемый `Clock` обеспечивает детерминированное тестирование. | Требует явной настройки форматирования на фронтенде. |
| **Вариант 2: Жестко зашитый фиксированный оффсет `+03:00`** | 1. Простота. | Риск нарушения стандартов: не учитывает правила IANA, не позволяет сменить локацию заведения без перекомпиляции кода. |
| **Вариант 3: Использование локального времени браузера пользователя** | 1. Естественно для глобальных сервисов. | Прямо противоречит `ASM-006`: если пользователь бронирует салон в Москве, находясь во Владивостоке или Калининграде, он увидит искаженное расписание смен мастеров. |

## Consequences

- В конфигурации приложения объявляется бин `ZoneId` и бин `Clock`.
- Автотест `AC-010` настраивается на запуск с эталонным часовым поясом `Europe/Moscow`.

## Requirements affected

- `NFR-005`, `BR-006`, `ASM-006`, `AC-010`, `AC-EDGE-005`, `AC-EDGE-008`, `RISK-002`.

- До старта реализации модуля расписания (Milestone 4).
