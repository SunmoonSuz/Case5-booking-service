# ADR-008: Представление денежных сумм и валюты

- Status: `ACCEPTED`
- Date: `2026-11-03`
- Decision owner: `Lead Backend Engineer`

## Context

В сущности `Service` (`REQ-003`, `REQ-010`) и карточке бронирования (`REQ-008`, `SCN-004`) присутствует стоимость услуги (`price`).
В исходном handoff тип данных и валюта явно не зафиксированы. Требуется определить:
1. Точный тип данных для хранения цены в БД и представления в коде бэкенда;
2. Формат передачи цены через REST API;
3. Валюту по умолчанию и правила форматирования в Web UI.

## Decision

Рекомендуется:

1. **Тип данных в PostgreSQL:** **`NUMERIC(10, 2)`**.
   - Две фиксированные цифры после запятой исключают ошибки округления чисел с плавающей точкой (`FLOAT`/`DOUBLE` строго запрещены).
   - Поддерживает суммы до 99 999 999.99, что с запасом покрывает любые цены услуг.
2. **Тип данных в Kotlin Backend:** **`java.math.BigDecimal`**.
   - С фиксацией масштаба (`scale = 2`, `RoundingMode.HALF_UP`).
   - Валидация при создании/редактировании услуги: `@DecimalMin(value = "0.00", inclusive = true)`.
3. **Валюта:**
   - По умолчанию принимается валюта **`RUB`** (Российский рубль), конфигурируемая через переменную окружения `APP_CURRENCY = RUB`.
   - В API стоимость передается числовым значением с двумя знаками (например, `1500.00`).
4. **Отображение в Web UI:**
   - Форматирование через стандартный `Intl.NumberFormat`:
     ```ts
     new Intl.NumberFormat('ru-RU', {
       style: 'currency',
       currency: 'RUB',
       maximumFractionDigits: 0
     }).format(price) // => "1 500 ₽"
     ```

## Alternatives considered

| Option | Benefits | Costs/Risks |
|---|---|---|
| **Вариант 1: `NUMERIC(10, 2)` / `BigDecimal` (Рекомендуется)** | 1. Общепринятый стандарт для финансовых полей в реляционных базах данных.<br>2. Прямая поддержка в Jackson и Spring Validation.<br>3. Читаемость при прямых SQL-запросах и в отчетах. | Небольшие накладные расходы объектов `BigDecimal` (несущественно для MVP). |
| **Вариант 2: Целое число в минимальных единицах (копейках) `BIGINT`** | 1. Высокая скорость арифметических операций. | Необходимость постоянной конвертации (деление/умножение на 100) при сериализации в API и валидации в UI, риск ошибок человеческого фактора при интеграциях. |
| **Вариант 3: `Double` / `Float`** | 1. Нативный примитив. | **Строго отвергнуто.** Накопление погрешностей двоичной плавающей точки (например, 0.1 + 0.2 != 0.3) недопустимо для денежных сумм. |

## Consequences

- Поле `price` в таблицах `services` и `bookings` имеет тип `NUMERIC(10, 2) NOT NULL`.
- API передает `price` как JSON Number/Decimal.

## Requirements affected

- `REQ-003`, `REQ-008`, `REQ-010`, `SCN-002`, `SCN-004`.
