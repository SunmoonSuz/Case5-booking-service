# ADR-012: Жизненный цикл каталога и правила модификации при наличии активных бронирований

- Status: `ACCEPTED`
- Date: `2026-11-03`
- Decision owner: `Lead Backend Engineer / System Analyst`

## Context

Администратор заведения имеет возможность модифицировать каталог: деактивировать мастеров, менять длительность и стоимость услуг, деактивировать услуги.
В реальной системе в этот момент могут существовать созданные клиентами будущие бронирования в статусах $S_{active} = \{ \text{PENDING}, \text{CONFIRMED} \}$.
В `SCN-005` (негативный сценарий E3) зафиксировано: «Попытка деактивировать мастера с активными подтверждёнными записями. Система выводит предупреждение: „У мастера есть активные записи. Сначала перенесите или отмените их“».
Необходимо формализовать правила для всех возможных мутаций каталога.

## Decision

Рекомендуется зафиксировать следующие правила:

### 1. Мягкое удаление (Soft Delete):
- Физическое удаление (`DELETE FROM services`, `DELETE FROM masters`) в базе данных запрещено на уровне внешних ключей (`ON DELETE RESTRICT`).
- Удаление сущностей в интерфейсе администратора выполняется через флаг мягкого удаления (`is_active = false`).
- Неактивные услуги и мастера автоматически скрываются из публичного каталога для клиентов и гостей (`GET /api/v1/services`, `GET /api/v1/masters`).

### 2. Правила деактивации мастера:
- Если у мастера имеются будущие записи ($start\_time > now$) в статусах $S_{active} = \{ \text{PENDING}, \text{CONFIRMED} \}$:
  - Операция деактивации отклоняется HTTP `400 Bad Request` с кодом `MASTER_HAS_ACTIVE_BOOKINGS`.
  - Администратор обязан предварительно отменить (`CANCELLED`) или отклонить (`REJECTED`) эти записи (`SCN-005` E3).
- Если активных предстоящих записей нет — мастер успешно переводится в `is_active = false`.

### 3. Правила деактивации услуги:
- При переводе услуги в `is_active = false` она перестает отображаться в каталоге, и по ней нельзя создать новые заявки.
- Уже созданные будущие заявки по этой услуге остаются в силе и могут быть подтверждены или обслужены (благодаря фиксации снимка данных в `Booking` согласно `ADR-011`).

### 4. Изменение параметров услуги (Длительность и Стоимость):
- **Изменение стоимости и названия:** разрешено в любой момент. Новая цена применяется только к новым бронированиям. Исторические и уже оформленные заявки сохраняют зафиксированную цену благодаря `ADR-011`.
- **Изменение длительности (30 мин $\leftrightarrow$ 60 мин):** если по данной услуге есть предстоящие активные записи ($start\_time > now$ в $S_{active}$), изменение длительности блокируется с ошибкой `400 Bad Request` (`CANNOT_MODIFY_DURATION_WITH_ACTIVE_BOOKINGS`). Для смены длительности администратору рекомендуется деактивировать старую услугу и создать новую, либо сначала отменить предстоящие визиты.

## Alternatives considered

| Option | Benefits | Costs/Risks |
|---|---|---|
| **Вариант 1: Запрет критичных мутаций при наличии будущих активных записей (Рекомендуется)** | 1. 100% защита клиентов от внезапного сдвига или поломки сетки расписания.<br>2. Полное соответствие сценарию `SCN-005` E3.<br>3. Предсказуемое и детерминированное поведение системы. | Требует явных действий администратора по отмене записей перед деактивацией мастера. |
| **Вариант 2: Автоматическая отмена (каскадный Cancel) всех записей при деактивации мастера** | 1. Операция выполняется в один клик. | Высокий риск потери клиентских записей без осознанного решения сотрудника. |
| **Вариант 3: Физическое удаление (Hard Delete)** | 1. Очистка таблиц. | **Критический дефект:** ломает внешние ключи истории бронирований клиентов, нарушает аудит. |

## Consequences

- Эндпоинты обновления и деактивации содержат предварительные проверки наличия активных предстоящих бронирований.
- Административный Web UI предоставляет понятные сообщения о причинах блокировки действия.
