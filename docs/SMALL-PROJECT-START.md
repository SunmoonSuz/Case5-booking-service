# Первый прогон на небольшом Kotlin Backend проекте

Цель: проверить работу связки аналитика → handoff → Kotlin developer → QA → code review на небольшом backend-only кейсе, не включая CI/CD и frontend.

## 1. Выберите небольшой кейс

Подойдёт один небольшой API/service с 2–4 функциональными требованиями, например:
- CRUD одного ресурса с простыми правилами;
- endpoint для расчёта/проверки значения;
- небольшой сервис с одной бизнес-операцией и сохранением результата.

Для первого прогона лучше не брать авторизацию сложного уровня, внешние интеграции, Kafka, сложную конкурентность или миграцию большой схемы одновременно.

## 2. Аналитика

В `analysis-project` создайте папку кейса из шаблона. В `01-intake.md` укажите:
- основной профиль `BACKEND_ONLY`;
- пользовательский frontend не нужен;
- основные входы/выходы API;
- бизнес-правила и ошибки;
- ограничения по Kotlin/JVM и допустимому framework, если они уже известны.

Запустите discovery и specification audit из аналитического `PROMPTS.md`. Не переносите в разработку неоднозначные правила как будто они подтверждены.

## 3. Инженерная папка

Скопируйте шаблон инженерного проекта в отдельный Git-репозиторий. Заполните:
- `docs/PROJECT-PROFILE.md`: `project_type: BACKEND_ONLY`;
- `docs/spec/IMPLEMENTATION-BRIEF.md`: согласованные REQ/AC и ссылки на полные документы.

Не оставляйте placeholder-ы в ключевых требованиях и не ставьте статус `APPROVED` без собственного подтверждения.

## 4. Первый запуск главного агента

Используйте запрос `Запустить небольшой backend-only Kotlin проект` из корневого `PROMPTS.md`. Сначала получите readiness check и технический план. Не разрешайте генерировать код до проверки требований и вашего согласования плана.

## 5. Проверка ролей

Ожидаемое поведение:
- главный агент читает профиль и brief;
- `developer` анализирует Kotlin/JVM репозиторий и реализует только backend;
- `frontend-developer` не вызывается;
- `tester` строит тест-план из REQ/AC и независимо запускает подходящие проверки;
- `strict-code-reviewer` проверяет diff в read-only режиме.

## 6. Что считать успешным тестовым прогоном комплекта

- Ни один агент не добавил неоговорённые функции или frontend.
- Каждое реализованное изменение связано с REQ/AC.
- Разработчик сообщил точные файлы, решения и реальные команды запуска.
- QA не копирует просто тесты разработчика, а проверяет наблюдаемое поведение и негативные случаи.
- Незапущенные проверки отмечены `NOT RUN`.
- Code review содержит конкретные доказательные замечания или объясняет, почему их нет.
- Пробный релиз не выполнялся без отдельного разрешения.

## 7. После первого прогона

Сохраняйте фактические проблемы в отдельном feedback-файле: неверно обнаруженный агент, неясные инструкции, ненужные технологии, пропущенный тест, повторяющиеся действия. Меняйте правила комплекта после наблюдаемого сбоя, а не ради абстрактного усложнения.
